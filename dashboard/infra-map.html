Context Worth knowing

The chatbot cannot send its own leads.
Web3Forms sits behind Cloudflare, which blocks requests from AWS datacenter IP addresses outright. The Lambda therefore builds a ready-to-send payload and hands it back to the visitor's browser, and that browser does the submitting. It is the same mechanism the plain static contact form already used, which posts to Web3Forms directly with no Lambda involved. Both paths end at Web3Forms, which emails the lead to KC.ITSolutions@outlook.com.
One IAM user gates every AWS action from this machine.
kcit-deploy is deliberately narrow: only kcit-* Lambda functions, only kcit-lambda-* IAM roles, only the one CloudFront distribution, plus read-only logs:FilterLogEvents on kcit-* log groups, that last one confirmed working directly rather than assumed. No EC2, no billing, nothing that can spend money outside that box. An AccessDenied from it is the policy doing its job.
Two repos, two trust levels.
kc.IT holds the site and chatbot source (deploy.ps1, chatbot/deploy-chatbot.ps1, chatbot/wire-cloudfront.ps1, chatbot/clients/*.json) and has no git remote at all, local only. kcit is the operations repo: the Obsidian vault of business knowledge plus .claude/agents/*.md, with a remote on GitHub at kevinchavez42069-afk/kcit. Nothing from kc.IT is on GitHub.
One Lambda serves every client.
kcit-chatbot is multi-tenant. Each client is a single JSON file under chatbot/clients/, currently kc-it-solutions.json and sample-plumbing.json, all sharing one prompt template. Adding a client is adding a file, not a function. Its Function URL is AWS_IAM-only and not publicly invokable; CloudFront reaches it through an Origin Access Control.
The dashboard is reachable off this machine, and now does more than show numbers.
The Lambda writes per-request input, output, cache-read and cache-write token counts as JSON lines to /aws/lambda/kcit-chatbot. cost-report.mjs pulls those through kcit-deploy, prices them and stores the result in costs.db, a local SQLite file that syncs nowhere; server.mjs serves it over Tailscale at http://100.87.11.96:7417. It's also where Kevin now chats with the agent fleet directly — executive-assistant read-only, the other three with real tool access gated by View 4's confirm-step.
The confirm-step is verified live, not just written.
Kevin ran the actual first test: asked client-onboarder to check git status, watched the confirm banner appear with the real command, approved it. A second table, agent_runs, logs what the fleet itself costs to run — separate from chatbot_usage, which is customer traffic — straight from the same SDK result the reply already carries, so there's no separate pricing table to keep in sync.
